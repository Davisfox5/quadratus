# Offline workflow scorecard

`python3 tools/workflow_scorecard.py --attestations review.json /saved/run1 /saved/run2` prints JSON. It reads saved `result.json`, `budget.json`, and `invocations.jsonl`; it does not execute the project or call a model. Run directory basenames must be unique in one scorecard.

An optional external `review.json` is keyed by run directory basename. A verified entry looks like:

```json
{"run1": {"status": "verified", "reviewer": "reviewer name", "evidence": "independent-review.txt", "source_fingerprint": "exact result.json source_fingerprint", "result_sha256": "SHA-256 of the reviewed result.json bytes"}}
```

The reviewer must create the evidence file in the run directory (or supply an absolute path), then record the SHA-256 digest of the exact `result.json` bytes they reviewed. The review should explain the original intended state, whether each task's declared requirements were appropriate, required checks, source-bound capture, actual review, settled requirements, and unresolved findings. The tool checks that the evidence file exists, the source and result identities match, and the saved workflow, requirements, findings and checks do not contradict completion. An omitted or malformed required flag is **unknown**. A false flag can be valid for a task; the reviewer must judge it against the original contract. Changing that flag or removing an edge after review invalidates `result_sha256`.

For completion evidence, the saved `workflow.run` and every task must carry their serialized outcome fields. Task contracts must declare typed `checks`, `design_review`, `security_verification`, `settlement`, and `design_evidence` requirements. The scorecard applies the engine's completion blocker rule to required edges, active terminal facts, closed tasks, and valid continuations or settled audit findings. A predecessor edge can be discharged only when the engine's saved facts support it. Final task and run check wrappers must pass. Run gate receipts carry `required`; any required receipt with a status other than `passed` contradicts the wrapper. Task gate receipts omit `required`, so the task's `passed` wrapper remains the available authority for optional gate failures. Earlier failed checks may be followed by a passing final receipt. A completed claim with a nonempty error is **unknown**. The independent attestation remains a human judgment; this tool cannot judge review quality or infer requirements that were never recorded.

The summary includes all selected runs and failed invocations. It reports the final budget interval, reserved attempts, invoked calls, failed calls, input and output tokens, and cached input as a subset of input. The run budget clock starts after repository scan, includes session readiness and plan-gate wait, and its final snapshot includes trace/report I/O. It is not an external supervisor clock and excludes operator time. The final `result.json` budget is authoritative when a result exists; an explicit null stays unknown. If its elapsed, attempt, or unknown-usage counters are behind the separately persisted budget, the conflicting field is unknown. Totals and their per-verified-completion ratios are null when unavailable or when no completion is verified. If reserved attempts and invocation events disagree, full token and spend totals stay unknown. An explicit unknown-usage count also makes token totals unknown. Historical cache counts in `diagnostics` are accepted when consistent with top-level values and no larger than input. `usage.jsonl` dollar values are API list-price counterfactuals and are excluded from observed spend. Only invocation `diagnostics.vendor_cost_usd` enters observed vendor spend; explicit zero is retained. A missing cost on any invoked call prevents a complete spend or spend-per-verified-completion figure. Subscription marginal spend, operator time, token usage outside saved invocations, and model judgment quality are not measured. The result is an observational scorecard, not a before/after efficiency claim.
