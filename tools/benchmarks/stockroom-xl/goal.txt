Add stock reservations, an event log, stock adjustments, an expiry sweep, bulk reservations and idempotency keys to stockroom, across the store, the HTTP API, the command line and the documentation. Standard library only (pytest for tests). Existing behaviour of add_item, get_item, list_items, GET /items, POST /items and the `list` and `add` commands must not change, and the existing tests must keep passing.

STORE (stockroom/store.py)
1. Schema version. `Store.schema_version()` returns 2. Opening a database written by the current code (an `items` table and nothing else) upgrades it in place: every item is kept unchanged, and opening it again changes nothing. A new database is created at version 2.
2. `Store.reserve(sku, quantity, holder, ttl_seconds, now=None)` holds stock and returns a dict with exactly these keys: `id` (a positive int, unique, never reused), `sku`, `quantity`, `holder` (as stored: stripped of surrounding whitespace), `expires_at` (a float, `now + ttl_seconds`) and `state` ("active").
3. `Store.release(reservation_id, now=None)`, `Store.commit(reservation_id, now=None)` and `Store.get_reservation(reservation_id, now=None)` each return the reservation dict in the same shape with its current state.
4. `Store.availability(sku, now=None)` returns `{"sku", "on_hand", "reserved", "available"}`: `on_hand` is the item's quantity, `reserved` the total quantity of its active reservations, `available` is `on_hand - reserved`.
5. `now` is a time in seconds (int or float); when omitted the store uses `time.time()`. A reservation whose state is active and whose `expires_at` is at or before `now` is expired: it reads with state "expired", it does not count as reserved, and it can never become active again.
6. States and transitions. reserve creates "active". release: active becomes "released"; a released reservation is returned unchanged; an expired one is returned with state "expired"; a committed one is refused with code `already_committed`. commit: active becomes "committed" and the item's quantity goes down by the reserved quantity; committed is refused with `already_committed`; released with `reservation_released`; expired with `reservation_expired`.
7. Refusals raise `StoreError` with these codes: `unknown_sku` (no such item), `invalid_quantity` (not an int, a bool, or less than 1), `insufficient_stock` (more than `available`), `invalid_holder` (not a str, empty after stripping, or longer than 64 characters after stripping), `invalid_ttl` (not an int, a bool, less than 1 or more than 86400), `unknown_reservation` (no reservation with that id; an id that is not a positive int is also `unknown_reservation`). Arguments are checked in this order: sku, quantity type and range, holder, ttl, then stock.
8. A refused call changes nothing in the database.
9. No overselling. When many threads, each with its own `Store` on the same file, reserve the same sku at the same time, the total quantity of active reservations never exceeds the item's quantity; the calls that do not fit are refused with `insufficient_stock`, and none fails any other way.

HTTP API (stockroom/api.py)
10. `POST /reservations` with a JSON object `{"sku", "quantity", "holder", "ttl_seconds"}` returns 201 and the reservation. `ttl_seconds` may be omitted and then is 900. `GET /reservations/<id>` returns 200 and the reservation. `DELETE /reservations/<id>` releases it and returns 200 and the reservation. `POST /reservations/<id>/commit` commits it and returns 200 and the reservation. `GET /items/<sku>/availability` returns 200 and the availability object.
11. Every error response from the new routes is a JSON object `{"error": code, "message": non-empty text}` with `Content-Type: application/json`. Statuses: 400 for `invalid_quantity`, `invalid_holder`, `invalid_ttl`, `invalid_json` (the body is not valid JSON, or not valid UTF-8), `invalid_body` (valid JSON that is not an object), `missing_field` (sku, quantity or holder absent), `unknown_field` (any key other than the four), `invalid_length` (Content-Length missing, not a non-negative decimal integer) and `invalid_id` (the <id> part is not a decimal integer of 1 to 18 digits with no sign, or is zero). 404 for `unknown_sku`, `unknown_reservation` and `not_found` (any other path). 405 `method_not_allowed` for a known path with another method. 409 for `insufficient_stock`, `already_committed`, `reservation_released` and `reservation_expired`. 413 `body_too_large` when Content-Length is more than 65536; the body is then not read.
12. JSON is read strictly: the constants NaN, Infinity and -Infinity are `invalid_json`, and a `quantity` or `ttl_seconds` that is a JSON number with a fraction or exponent (for example 2.0 or 2e0) is `invalid_quantity` or `invalid_ttl`.
13. A request that gets an error response changes nothing in the database.

COMMAND LINE (stockroom/cli.py)
14. New commands: `reserve SKU QUANTITY HOLDER [--ttl SECONDS]` (default 900), `release ID`, `commit ID`, `show ID` and `availability SKU`. On success each prints exactly one line on stdout, a JSON object (the reservation, or the availability object), prints nothing on stderr, and `main` returns 0.
15. Every failure of the five new commands prints exactly one line on stderr, a JSON object `{"error": code, "message": non-empty text}`, prints nothing on stdout, and `main` returns a status without raising `SystemExit`: 1 for a store refusal (with the store's code), 2 with code `usage` for anything the command line itself rejects, including a QUANTITY, ID or --ttl value that is not a decimal integer, a missing argument and an extra argument.
16. `main(argv)` keeps its signature. The `list` and `add` commands behave exactly as they do now, including what happens when their arguments are rejected.

DOCUMENTATION
17. README.md documents the new Store methods, the new routes and the new commands, with the reservation states and what expiry means.
18. A new file docs/errors.md has a Markdown table with one row for every error code named in this goal (store codes, HTTP-only codes and `usage`), with columns for the code, the HTTP status (or a dash where the code never reaches HTTP) and a one-line meaning.

EVENT LOG (stockroom/store.py)
19. The store keeps an append-only event log. An event is a dict with exactly these keys: `id` (a positive int, increasing in the order events were recorded, never reused), `at` (a float), `kind`, `sku`, `quantity` (an int), `reservation_id` (an int or None) and `holder` (a str or None).
20. Exactly one event is recorded for each of these, and for nothing else. A successful add_item: kind "item_added", quantity the item's quantity, reservation_id None, holder None, `at` from `time.time()`. A successful reserve: "reserved", with the reservation's quantity, id and holder, `at` the call's `now`. A release that changes an active reservation to released: "released", same fields. A successful commit: "committed", same fields. A successful adjust (item 22): "adjusted", quantity the delta, reservation_id None, holder None. Each reservation a sweep records (item 25): "expired". A release that changes nothing, a read, and any refused call record no event.
21. `Store.events(sku=None, kind=None, after_id=0, limit=100)` returns a list of events in ascending id order whose id is greater than `after_id`, only those with that sku and that kind when given, at most `limit` of them. Refusals, checked in this order: `invalid_kind` (kind is given and is not one of the six kinds), `invalid_cursor` (after_id is not an int, is a bool, or is negative), `invalid_limit` (not an int, a bool, less than 1 or more than 500). An sku no item has is not an error: the list is empty.

ADJUSTMENTS (stockroom/store.py)
22. `Store.adjust(sku, delta, reason, now=None)` changes the item's quantity by `delta` and returns the availability object of item 4 as it is after the change.
23. Refusals, checked in this order: `unknown_sku`; `invalid_delta` (not an int, a bool, or zero); `invalid_reason` (not one of "restock", "damage", "correction"); then, with new = on_hand + delta: `insufficient_stock` when new is below zero, otherwise `stock_reserved` when new is below the total quantity of active reservations at `now`.
24. No lost updates. When many threads, each with its own `Store`, adjust the same sku at the same time, every successful delta is applied exactly once; and adjustments racing with reservations never leave the item's quantity below the total of its active reservations.

SWEEP (stockroom/store.py)
25. `Store.sweep(now=None)` takes every reservation that is expired at `now` and has no "expired" event yet, in ascending reservation id order, records one "expired" event for it (the reservation's sku, quantity, id and holder, `at` the sweep's `now`), and returns how many it recorded. This holds whether or not an earlier read already showed the reservation as expired. A sweep that finds none returns 0 and records nothing. After a sweep the reservation reads as "expired" at any `now`.

BULK RESERVATIONS (stockroom/store.py)
26. `Store.reserve_many(lines, holder, ttl_seconds, now=None)` reserves every line or none. `lines` is a list of 1 to 20 pairs `[sku, quantity]` (each a list or tuple of exactly two). It returns the list of reservation dicts in the order of the lines; all have the same `expires_at`; one "reserved" event is recorded per line, in line order.
27. Refusals, checked in this order: `invalid_lines` (not a list, empty, more than 20 entries, an entry that is not a list or tuple of exactly two, or the same sku in two lines); then for each line in order its sku (`unknown_sku`) and its quantity (`invalid_quantity`); then `invalid_holder`; then `invalid_ttl`; then `insufficient_stock` for the first line that does not fit. A refused call changes nothing and records no event.

IDEMPOTENCY KEYS (stockroom/store.py)
28. `reserve` and `adjust` accept a keyword argument `idempotency_key=None`. A key is a str of 1 to 64 characters, each one of A-Z, a-z, 0-9, underscore or hyphen; anything else given as a key is refused with `invalid_idempotency_key`, before every other check.
29. When a call with a key succeeds, the store remembers the key with the operation (reserve or adjust), its arguments (for reserve: sku, quantity, the stripped holder, ttl_seconds; for adjust: sku, delta, reason) and the value it returned. A later call with a remembered key is decided before any other check: with the same operation and arguments it returns the remembered value, changes nothing and records no event; with a different operation or different arguments it is refused with `idempotency_conflict`. `now` is not part of the comparison. A refused call remembers nothing. Keys never expire.
30. When many threads, each with its own `Store`, make the same reserve call with the same key at the same time, exactly one reservation is created and every call returns that reservation.

HTTP API, CONTINUED (stockroom/api.py)
31. `GET /events` returns 200 and `{"events": [...]}`. Optional query parameters: `sku`, `kind`, `after` (the after_id) and `limit`. Errors, status 400: `invalid_kind`; `invalid_cursor` (`after` is not 1 to 18 decimal digits); `invalid_limit` (`limit` is not 1 to 18 decimal digits, or is outside 1 to 500); `unknown_parameter` (any other query key); `duplicate_parameter` (a key given more than once).
32. `POST /items/<sku>/adjustments` with a JSON object `{"delta", "reason"}` returns 200 and the availability object. `POST /sweep` with the JSON object `{}` returns 200 and `{"expired": n}`. `POST /bulk-reservations` with a JSON object `{"lines", "holder", "ttl_seconds"}` (ttl_seconds optional, 900 when omitted) returns 201 and `{"reservations": [...]}`.
33. The request-body rules of items 11 to 13 apply to these three routes with their own field names: `invalid_json`, `invalid_body`, `missing_field` (delta or reason; lines or holder), `unknown_field` (for /sweep, any key at all), `invalid_length`, `body_too_large`, and a `delta` or a line quantity that is a JSON number with a fraction or exponent is `invalid_delta` or `invalid_quantity`. Statuses: 400 for `invalid_delta`, `invalid_reason`, `invalid_lines` and `invalid_idempotency_key`; 404 for `unknown_sku`; 409 for `insufficient_stock`, `stock_reserved` and `idempotency_conflict`; 405 `method_not_allowed` for these paths and /events with another method.
34. The request header `Idempotency-Key` on `POST /reservations` and `POST /items/<sku>/adjustments` is passed to the store as the key. A replayed request gets the same status and the same body as the first one. On every other route the header is ignored.
35. A request that gets an error response changes nothing and records no event.

COMMAND LINE, CONTINUED (stockroom/cli.py)
36. New commands: `adjust SKU DELTA REASON [--key KEY]` prints the availability object, and DELTA may be negative (for example `adjust A-1 -3 damage`); `sweep` prints `{"expired": n}`; `events [--sku SKU] [--kind KIND] [--after ID] [--limit N]` prints `{"events": [...]}`; `reserve-many HOLDER SKU=QTY [SKU=QTY ...] [--ttl SECONDS]` prints `{"reservations": [...]}`; and `reserve` accepts `--key KEY`.
37. Items 14 and 15 apply to these commands as they do to the five reservation commands: one JSON line on stdout and status 0 on success; on failure one JSON line on stderr, nothing on stdout, status 1 for a store refusal and status 2 with code `usage` for anything the command line itself rejects, including a DELTA, --after or --limit value that is not a decimal integer (DELTA may carry one leading minus sign), a SKU=QTY argument with no "=", an empty SKU or a QTY that is not a decimal integer, a missing argument and an extra argument.

DOCUMENTATION, CONTINUED
38. README.md also documents the event log, adjust, sweep, reserve_many, idempotency keys, the new routes and the new commands. docs/errors.md also has a row for each of: `invalid_kind`, `invalid_cursor`, `invalid_limit`, `invalid_delta`, `invalid_reason`, `stock_reserved`, `invalid_lines`, `invalid_idempotency_key`, `idempotency_conflict`, `unknown_parameter` and `duplicate_parameter`.

TESTS
39. Each numbered item above (1 to 38) that states behaviour has tests in tests/, including a test per refusal code, a test that a refused call or request leaves the database unchanged, and tests of items 9, 24 and 30 that run real threads. `python -m pytest -q` passes.
